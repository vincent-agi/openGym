# Architecture

## Components

```
                         HTTPS (your reverse proxy / tunnel)
 Browser / PWA ─────────────────────────────────────────────┐
                                                             ▼
                                              ┌──────────────────────────────┐
                                              │ web  (nginx 1.27, port 80)   │
                                              │  /            static SPA     │
                                              │  /img/ /gif/  media (ro vol) │
                                              │  /api/  ──────────────┐      │
                                              └───────────────────────┼──────┘
                                                                      ▼  http://api:3000
                                              ┌──────────────────────────────┐
                                              │ api  (Node 22, port 3000)    │
                                              │  no framework                │
                                              │  WebAuthn · sessions · sync  │
                                              │  Web Push · presence · admin │
                                              └───────────────┬──────────────┘
                                                              ▼  bind mount
                                                         ./data  (JSON files)

 media (one-shot, alpine/git) ── clones the exercise dataset into ./media/{img,gif}
```

| Service | Source | Image | Role |
|---|---|---|---|
| `web` | `web/Dockerfile`, `web/nginx.conf` | `ghcr.io/duartesantos8/opengym-web` | Multi-stage build: `node:22-alpine` builds the Vite app, `nginx:1.27-alpine` serves it and proxies `/api/`. |
| `api` | `api/Dockerfile`, `api/server.js` | `ghcr.io/duartesantos8/opengym-api` | One Node file. Passkey auth, per-user state storage, push, admin. |
| `media` | inline in `docker-compose.yml` | `alpine/git` | One-shot job: `git clone --depth 1` of `hasaneyldrm/exercises-dataset` into `./media/img` and `./media/gif` if `./media/img` is empty. `restart: "no"`. |

`web` waits for `media` to complete (`service_completed_successfully`) and for `api` to start (`service_started`, not
healthy — there is no healthcheck).

## Why one origin

WebAuthn binds credentials to an exact hostname (`RP_ID`), and the browser enforces the origin. nginx therefore
serves the SPA **and** proxies `/api/` on the same host and port, so the browser sees a single origin and the API
needs no CORS handling.

## Build flavours of the frontend

One codebase, three builds, selected at build time by Vite env flags:

| Flavour | Flag | Backend | Storage | Use |
|---|---|---|---|---|
| **Self-hosted web** (default) | none | `api` service | Server JSON + browser `localStorage` | The product. |
| **Demo** | `VITE_DEMO=1` | none | Browser only, seeded example data | GitHub Pages demo. Seed generator is imported dynamically so it never ships in the normal bundle. |
| **Mobile** | `VITE_MOBILE=1` (+ `VITE_IMG_BASE`, `VITE_GIF_BASE`) | none | Capacitor file `opengym-state.json` mirrored from `localStorage` | Android APK / iOS app. Media from jsDelivr, pinned to a dataset commit. |

## Frontend

- **React 19 + Vite**, `HashRouter` (so the static server needs no rewrite rules for routes; nginx still has an SPA
  fallback).
- **State:** one Zustand store (`src/store/useStore.js`) holding the whole user state object `S`. Every change goes
  through `update(mutator)`: clone → mutate → persist to `localStorage` (`gym_state_v1`) → debounce a push to
  the server (1.5 s). UI-only state (sheets, toasts, timers) is in `src/store/useUI.js`.
- **Pure logic** (progression, 1RM, history reading, import parsers, nutrition, goals) lives in `src/lib/` with Vitest
  tests beside it. Anything that decides a training number must be a pure function there.
- **i18n:** `src/lib/i18n.js`. English strings are the keys; the 11 other languages are lazy-loaded packs in
  `src/locales/`. Exercise instruction packs (`src/instr/`) are generated by `scripts/build-instructions.mjs`.
- **Service worker** (`public/sw.js`): media cache-first, everything else network-first with offline fallback to
  `index.html`; never caches `/api/`. Also displays Web Push notifications.
- **Exercise catalogue** (`src/lib/exercises-data.js`, ~900 KB) is split into its own chunk.

### Sync model

The server is a **dumb document store**; all merge logic is on the client.

1. Boot: `GET /api/me`; if signed in, `GET /api/data`.
2. Pull rule: the server copy replaces local when local has no data, **or** when `server._ts >= local._ts` and local is
   not marked dirty (`gym_dirty`). Otherwise local data is pushed.
3. Every local change stamps `_ts = Date.now()` and schedules `PUT /api/data` with the **entire** state.
4. A failed push sets `gym_dirty`; the next pull then prefers local.
5. `state.active` (the in-progress workout) is **deleted server-side on PUT** and preserved client-side on pull —
   an unfinished workout never leaves its device.

Consequence: **last write wins, per whole profile.** Two devices editing offline will overwrite each other's
changes; the later `_ts` wins. There is no field-level merge and no server-side version check.

## Backend (`api/server.js`)

A single ES module of ~580 lines using `node:http`. No router, no middleware: a `routes` object keyed by
`"METHOD /path"`.

### Startup sequence

1. Read env (`PORT`, `DATA_DIR`, `RP_ID`, `ORIGIN`, `RP_NAME`, `ADMIN_UIDS`, `INVITE_ONLY`, `SESSION_DAYS`,
   `VAPID_SUBJECT`).
2. `mkdir -p $DATA_DIR`.
3. Load or create `secret` (32 random bytes, hex, mode `0600`).
4. Load `db.json` (**falls back to an empty database on any read/parse error** — see
   [data-model](data-model.md#integrity-and-failure-modes)).
5. Load or generate `vapid.json` (mode `0600`) and configure `web-push`.
6. Start background timers and listen on `PORT`.

### Background timers (all `unref`'d)

| Interval | Purpose |
|---|---|
| 10 s | Workout-day reminder: for each user with a push subscription and `reminder.on`, compute "now" in the user's IANA time zone; if it matches `reminder.time`, no workout is logged today and a routine is planned, push once per day (`user.lastReminder`). Reads each such user's state file. |
| 60 s | Purge expired WebAuthn challenges. |
| 30 s | Purge expired presence entries. |

### In-memory state (lost on restart)

| Structure | TTL | Purpose |
|---|---|---|
| `challenges` | 5 min | WebAuthn registration/login challenges, one-shot. |
| `presence` | 70 s | "Training now" data for the admin dashboard (client pings every 20 s). |
| `restTimers`, `pressureReliefTimers` | seconds | Scheduled push for rest-end / pressure-relief when the tab is backgrounded. |

A restart therefore drops in-flight sign-ins (the user just retries) and pending rest-timer pushes. It does not
lose any stored data.

### Request handling

`http.createServer` → look up `routes[method + " " + pathname]` → 404 `{"error":"not found"}` if absent →
run handler in `try/catch` → 500 `{"error":"server error"}` on exception. Bodies are JSON, capped at **5 MB**
(`MAX_BODY`). All JSON responses carry `Cache-Control: no-store`. See the [API reference](api-reference.md).

### Authentication

- **WebAuthn** through `@simplewebauthn/server` v13. Registration requires a resident key
  (`residentKey: required`), `userVerification: preferred`, attestation `none`. Login uses discoverable credentials
  (`allowCredentials: []`), so no username is typed.
- **Session** = cookie `gymsid` = `<uid>:<expiryMs>:<sv>.<HMAC-SHA256 base64url>`. `sv` is a per-user counter;
  bumping it (`POST /api/logout/all`) invalidates every cookie ever issued. See [Security](security.md).

## Design decisions worth knowing

| Decision | Rationale | Cost |
|---|---|---|
| JSON files, no database | `docker compose up` with zero dependencies; backup = copy a folder. | No transactions, no concurrency, no queries, whole-file rewrites. |
| Whole-state sync | Trivial server, offline-first client. | Last-write-wins; payload grows with history. |
| No framework, 2 runtime deps | Small attack surface, easy to audit. | Hand-rolled routing, no rate limiting, no input schema validation. |
| Passkeys only | No password storage, no reset flow to attack. | No recovery. One passkey per profile. |
| TLS and rate limiting delegated to the reverse proxy | Keeps the app small. | Operator must supply both; defaults are not safe on the open internet. |

## Hard limits

Design the deployment around these.

1. **Single process, single host.** `db.json` is held in memory and rewritten in full on each change; timers, challenges
   and presence are in process memory. Running two `api` replicas against the same `./data` will lose writes and
   break sign-in (a challenge issued by one replica is unknown to the other). **Do not scale horizontally.**
2. **Whole-database rewrite.** Every registration, login (counter update), push subscribe or admin action rewrites
   `db.json` (pretty-printed). Fine for tens to low hundreds of users; it does not scale to thousands.
3. **Request body ≤ 5 MB in the API, but ≤ 1 MB at nginx.** The shipped `web/nginx.conf` sets no
   `client_max_body_size`, and nginx's default is **1 MB**. A user whose full state exceeds 1 MB (years of history,
   large imports) gets **HTTP 413** from nginx on `PUT /api/data` and **stops syncing** (the client keeps retrying and
   stays `dirty`). Raise it in both nginx layers if you expect this — see
   [Deployment](deployment.md#request-size).
4. **Reminder loop reads state files** of users with push enabled every 10 s.
5. **No rate limiting, no CSRF tokens, no security headers** in the app or the shipped nginx config.
6. **Time-based features use the server clock** for sessions and invites, and the user's reported IANA zone for
   reminders.
